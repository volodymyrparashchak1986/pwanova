# PWANova

**The distribution layer for the open web.** Discover. Trust. Install.

PWANova is a consumer app discovery and distribution platform for modern web apps, installable web apps and PWAs. Launch boards help apps get noticed; PWANova helps them stay discovered: ratings, reviews, verification, install guidance, analytics and developer reputation.

> Build anywhere. Launch anywhere. Live on PWANova.

Stack: Next.js 16 (App Router) · TypeScript · Tailwind CSS 4 · shadcn/ui (Base UI) · Lucide · Supabase (Auth, Postgres, RLS, Storage) · Vercel.

**Status: closed beta.** See [`docs/beta-audit.md`](docs/beta-audit.md) for what was found and fixed to get here, [`docs/beta-pilot.md`](docs/beta-pilot.md) for the pilot plan, and [`docs/beta-release-checklist.md`](docs/beta-release-checklist.md) before inviting anyone.

## Quick start (demo mode, no credentials)

```bash
npm install
npm run dev
```

With no Supabase variables set, PWANova runs in **read-only demo mode** on 15 fabricated apps (a banner says so). Home, Explore, search, filters, app pages, categories, developer pages, dashboard preview, the public API, embeds and the PWA all work. Anything that writes (sign-in, ratings, reviews, favorites, ship, claim, admin) needs Supabase and says so instead of pretending.

All demo listings are flagged `is_demo`, labelled "Demo data" in the UI, use the reserved `.example` TLD (the sites do not exist) and are `noindex`.

## Set up Supabase

1. Create a project at [supabase.com](https://supabase.com).
2. **Apply the schema.** Either:
   - CLI: `supabase link --project-ref <ref> && supabase db push`, or
   - SQL editor: run the files in `supabase/migrations/` in filename order.
3. **(Optional) Load demo data**: run `supabase/seed.sql` in the SQL editor (it is generated by `npm run seed:generate` and flagged `is_demo`). **Do not seed production.** Demo users are inserted without credentials (empty password hash, never confirmed) and cannot sign in; the rows are complete so the dashboard's Authentication → Users page keeps working. Even if seeded, `is_demo` rows stay out of every public listing/search/ranking/sitemap/partner-API response unless you explicitly set `SHOW_DEMO_DATA=true` (see below) — but the simplest safe rule is still: don't seed a project with real users. To remove all demo data later, run `supabase/unseed.sql`.
4. **Environment**: copy `.env.example` to `.env.local` and fill in:

   | Variable | Where to find it |
   | --- | --- |
   | `NEXT_PUBLIC_SUPABASE_URL` | Project Settings → API |
   | `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Project Settings → API → the **legacy `anon`** JWT key |
   | `SUPABASE_SERVICE_ROLE_KEY` | Project Settings → API → the **legacy `service_role`** JWT key. **Server only. Never expose it.** |
   | `NEXT_PUBLIC_SITE_URL` | Your public origin, e.g. `https://pwanova.app` |

   With the CLI: `supabase projects api-keys --project-ref <ref>`. The legacy JWT keys are used because they are what the whole stack (supabase-js, `@supabase/ssr`, PostgREST, Auth admin API) was verified with. The newer `sb_secret_…` keys are **masked** by the Management API/CLI, so copy them from the dashboard if you switch; that path was not tested here.

5. **Auth providers** (Authentication → Providers):
   - **Email**: enabled by default (magic link).
   - **Google** and **GitHub**: create OAuth apps and paste client id/secret. Use the callback URL shown by Supabase (`https://<ref>.supabase.co/auth/v1/callback`).
   - Authentication → URL Configuration: set **Site URL** to `NEXT_PUBLIC_SITE_URL` and add `<site>/auth/callback` (plus `http://localhost:3000/auth/callback`) to **Redirect URLs**.
6. **Make yourself an admin** (after signing in once):

   ```sql
   update public.profiles set role = 'admin' where username = 'your-username';
   ```

### Why a service role key?

The service role is used **only on the server** (`src/lib/supabase/admin.ts` is `server-only`) for things a visitor must not be able to fake:

- event ingestion (`app_events` has no public insert policy),
- recording ownership verification results and granting `verified_owner`,
- writing quality checks (`app_checks`) and the `verified` status,
- the shared rate-limit counter.

Without it PWANova still works, but events are not recorded, ownership verification is unavailable and rate limits fall back to per-instance memory.

## Data model

Migrations live in `supabase/migrations/`:

| File | Contents |
| --- | --- |
| `…_schema.sql` | Tables (`profiles`, `apps`, `app_screenshots`, `ratings`, `reviews`, `review_helpful`, `developer_responses`, `favorites`, `app_events`, `partners`, `app_sources`, `app_checks`, `reports`, `partner_referrals`, plus `app_claims`, `rate_limits`), triggers, DB-level throttles |
| `…_rls.sql` | Row Level Security policies for every table |
| `…_views.sql` | `apps_public` view (aggregates, `ranking_score`, `trending_score`, search text), `rating_breakdown()`, `developer_dashboard()` |
| `…_storage.sql` | Public `app-media` bucket with per-user write folders |
| `…_beta_hardening.sql` | `moderation_note` + `rejected` app status; `app_claims.expires_at`; atomic `claim_app_ownership()`; `admin_actions` audit log; DB-level self-rating/review ban; re-verification on domain/URL change; `purge_old_events()`. Additive only — see [`docs/beta-audit.md`](docs/beta-audit.md). |

Notable decisions:

- `app_checks` booleans are nullable: `NULL` means *unknown*, never a guess. Offline and push support show as `—` because they cannot be verified from outside an app.
- **Four separate attribution concepts:** `app_sources.source_type = 'launched_on'` (launch source: where the app first launched — set once, never overwritten by a later referral), `'discovered_via'` (discovery source, when different from the launch), `partner_referrals` / `app_events.partner_id` (referral partner — only an actual match in the `partners` table counts; an arbitrary `?ref=anything` is stored in a cookie but never treated as an official partner) and `app_events.source` (traffic channel bucket). See `/partners` on the running site for the user-facing explanation.
- Protected columns (`ownership_status`, `verification_status`, `is_featured`, `is_pwa`, `is_installable`, `domain`, `url`, `moderation_note`, review trust flags, profile `role`) are locked by triggers; only admins and the service role can change them. A non-admin owner may only toggle `status` between `published` and `hidden`, and only starting from one of those two — never out of `pending`, `rejected` or `suspended` (a real bug in an earlier version let an owner self-approve; see the audit).
- Only the **verified owner** of an app can post developer responses.
- An app's own developer can neither rate nor review it — enforced by a database trigger, not just the UI.
- Ownership assignment (`claim_app_ownership()`) is a single conditional `UPDATE`, so two verification attempts for the same app can never both succeed, and a normal claim can never replace an app that already has a verified owner. A disputed reassignment is a separate, logged admin action (`reassignOwner`).
- Claim tokens expire after 3 days (`app_claims.expires_at`); restarting a claim issues a fresh one.

### Ranking

`ranking_score` is a Bayesian-style weighted rating (prior 3.8, weight 10) plus capped log-scaled reviews, saves, 30-day opens, 7-day recency and quality checks. One perfect rating cannot take #1. Implemented in SQL (`ranking_score`) and mirrored in `src/lib/ranking.ts`; a test asserts the two agree. `trending_score` weighs the last 7 days of opens, saves, reviews and ratings.

### Install experience (and its honest limits)

Browsers only let a site trigger the install prompt for **its own** origin, so PWANova cannot one-click install another site's app — and does not try to. The Install dialog for a listed app (`src/components/app/install-dialog.tsx`) never touches `beforeinstallprompt` at all: an earlier version did, which meant clicking "Install {App}" could silently trigger a prompt to install **PWANova itself**, mislabelled. That bug and its fix are documented in `docs/beta-audit.md` (row P0-3) and guarded by `tests/install-dialog.test.ts`. The dialog opens platform-specific guidance (iPhone/Safari: Share → Add to Home Screen → Add; Android: menu → Install app; desktop: address-bar install icon) that always explains it's leaving PWANova for the app's own domain.

`install_click` is an **install intent**, not a confirmed install. The UI says "Install actions" and never claims installs.

### Public API

```
GET /api/public/apps/by-domain?domain=example.com
```

CORS-enabled, cached, rate limited to 60 req/min/IP, public fields only (no email, user id or token). Returns name, slug, rating (`null` when there are no ratings yet, not `0`), ratingsCount, reviewsCount, verified, installable, pwa, host, per-check status (`checks.*`, each `true`/`false`/`null` — `null` means not checked, never rendered as a pass), lastCheckedAt, developer and links to the PWANova page, install guidance, the SVG badge and the iframe embed. A hidden/suspended/pending/rejected app 404s here, in `/api/badge/[slug]` and in `/embed/app/[slug]` alike.

Two embed formats:
- `<iframe src="/embed/app/{slug}">` (`?theme=dark` optional); only `/embed/*` may be framed by third parties.
- `<img src="/api/badge/{slug}">` — a plain, XML-escaped SVG, no JavaScript required.

`/partners` has a live generator for both (pick an app, format and theme; copy the snippet), and `/partners/demo` is a clearly-labelled fictional worked example ("Vibeboard") showing a before/after and the real, working badge.

### Partner attribution

Visiting any page with `?ref=<partner>` or `?source=<partner>` stores a 30-day `pwn_ref` cookie. Events log `partner_id` **only when that code matches a real row in `partners`** — an arbitrary `?ref=anything` is still stored in the cookie (harmless) but is never treated as an official partner. The app's `launch_source` is untouched by a referral, and a `partner_referrals` row is created when that visitor ships an app. See "Four separate attribution concepts" above.

## Security

- All URL fetching is **server-side** and goes through `src/lib/security/ssrf.ts`: http(s) only, default ports only, no credentials, blocks localhost / `.local` / `.internal` / private, loopback, link-local and CGNAT ranges (IPv4 + IPv6), re-validates every redirect hop, resolves DNS *inside* the socket lookup to defeat DNS rebinding, and caps time and size. Remote pages are parsed as text and never executed or framed.
- User text is stripped of tags/control characters; only http(s) URLs are accepted for links and images (`javascript:` / `data:` rejected); JSON-LD is escaped.
- Rate limits on submit, ratings, reviews, reports, analysis, events and the public API (DB-backed when the service role key is present), plus DB triggers on reviews, reports and app submissions.
- Security headers via `next.config.ts` (HSTS, nosniff, frame protection except `/embed`).
- Open-redirect protection on `next=` after sign-in.
- Self-rating/self-review, owner self-approval and ownership takeover are all blocked at the database level (triggers/atomic functions), not only in the server actions — see `docs/beta-audit.md` for the three real bugs this caught.

## Testing and validation

```bash
npm run typecheck     # tsc --noEmit
npm run lint          # eslint
npm test              # 86 tests (see below)
npm run build         # production build
npm run validate      # all of the above
npm run verify:supabase   # 34 live checks against the project in .env.local (see below) — NOT run against
                           # a real project since the beta-hardening pass; see docs/beta-audit.md
```

`npm test` runs the **real migrations and seed** on an in-process Postgres ([PGlite](https://pglite.dev)) with the Supabase `auth`/role pieces stubbed (`tests/supabase-prelude.sql`), and checks: public reads, duplicate-rating prevention, review ownership, forged trust flags, helpful votes, developer-response permissions (verified owner only), favorites isolation, protected columns, self-promotion blocking, event write blocking, admin powers, rate-limit function privileges, SQL/TS ranking parity, "one 5.0 rating is not #1", the DB-level self-rating/review ban, atomic ownership assignment (including a simulated race), re-verification on domain change, append-only admin audit log, raw-event retention, and that a non-admin can never self-approve a pending/rejected app. Unit tests cover URL/SSRF validation, sanitisation, traffic classification, host and platform detection, search, claim-token expiry and the partner badge's XML escaping. `tests/install-dialog.test.ts` is a source-level regression guard against the `beforeinstallprompt` bug described in `docs/beta-audit.md`.

`npm run verify:supabase` runs against your **real** Supabase project (needs `.env.local`). It creates throw-away users and rows, then deletes them. It checks the same rules as above through real Auth, PostgREST, RLS, triggers, RPCs and Storage: forged trust flags, protected columns, claim tokens, ratings/reviews/helpful/favorites, developer responses, events and the analytics RPC, admin powers, Storage folder isolation and MIME limits, service-only functions, and that the Auth admin API can list users. It has not been extended with the beta-hardening checks yet (atomic claim, self-rating ban, audit log) — add them before relying on it as the live counterpart to the new `tests/db.test.ts` cases.

**Not covered by automated tests:** real Google/GitHub/magic-link sign-in (the OAuth providers must be configured in your project first), the *success* path of ownership verification against a domain you control (the token-matching helpers are unit-tested; the failure path was exercised live), and a real phone (the install-dialog fix and mobile layout were only checked with an emulated viewport — see `docs/beta-pilot.md`'s manual checklist). Local Supabase via `supabase start` needs Docker.

## Deploy to Vercel

Live (demo data, `noindex`): https://pwanova.vercel.app

1. Push the repo and import it in Vercel (framework: Next.js; no build overrides).
2. Add environment variables (Production + Preview): `NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `CRON_SECRET` (any long random string), optionally `SUBMIT_REQUIRES_APPROVAL=true`, and, at launch, `ALLOW_INDEXING=true`. Leave `SHOW_DEMO_DATA` unset/`false` on every environment that might have real users (see `docs/beta-release-checklist.md`).
3. Add your production URL to Supabase's redirect URLs (see above).
4. `vercel.json` schedules `/api/cron/health` daily; Vercel sends `Authorization: Bearer $CRON_SECRET` automatically. It re-checks the 10 least-recently checked apps per run, updating quality checks, health status and verified status.
5. Deploy. Either use Vercel's Git integration, or the bundled GitHub Actions job (useful when the repo owner is a different GitHub account than the Vercel account): after CI passes on `main`, `.github/workflows/ci.yml` runs `vercel deploy --prod`. Enable it once:
   ```bash
   # 1. create a token at vercel.com/account/tokens (scope: your team), then store it as a secret
   gh secret set VERCEL_TOKEN
   # 2. the project/org ids are in .vercel/project.json after `vercel link`
   gh variable set VERCEL_ORG_ID --body team_xxx && gh variable set VERCEL_PROJECT_ID --body prj_xxx
   # 3. switch the deploy job on
   gh variable set VERCEL_DEPLOY --body true
   ```
   Manual deploys also work: `vercel deploy --prod` from a linked folder (`.vercelignore` keeps local `.env*` files out of uploads). PWANova is itself an installable PWA (manifest, icons, service worker, offline page).
6. Set the Supabase Auth **Site URL** and **Redirect URLs** to your production origin (`supabase/config.toml` + `supabase config diff` to review, then `supabase config push`). Never run `config push` blindly: it applies immediately and overwrites remote settings with the local file.

Set `SUBMIT_REQUIRES_APPROVAL=true` to hold new submissions as `pending` until an admin approves them in `/admin` (owners can still verify ownership of their pending app from the claim page).

**Search engines:** the site is `noindex` and `robots.txt` disallows everything until you set `ALLOW_INDEXING=true`. Do that only after removing demo data (`supabase/unseed.sql`).

`vercel.json` pins functions to `fra1` (Frankfurt) to sit next to a Frankfurt Supabase project. Change it to match your Supabase region.

## Notes

- The `shadcn` CLI once pulled in an unrelated npm package named `cn`. It was removed and `src/lib/utils.ts` uses `clsx` + `tailwind-merge`. If you re-run `shadcn add`, check the diff for `from "cn"` imports.
- shadcn on Base UI renders `<button type="button">` by default. Any button that should submit a form needs an explicit `type="submit"`.
- Third-party names (Vercel, v0, Product Hunt, …) appear only as neutral attribution badges and imply no endorsement or partnership. Demo partners are placeholders.

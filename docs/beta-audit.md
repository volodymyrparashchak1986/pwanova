# PWANova beta audit

**Date:** 2026-09-22 · **Branch:** `beta/hardening` · **Scope:** turn the existing MVP into a closed beta safe to show real developers and launch-board owners, per the brief in this branch's commit history.

**Method:** read every migration, RLS policy, server action, API route and the pages that call them; cross-checked against a fresh read of `README.md`, `package.json`, `.env.example` and `tests/*`. Three real bugs were found this way (rows **P0-1, P0-2, P0-3** below) — not hypothetical gaps, but code that does the wrong thing today. All three are fixed on this branch, with a regression test each. Everything in the table was independently re-verified after the fix (see the "How verified" column and the per-item detail below); nothing here is a recommendation that wasn't also implemented and tested, except where explicitly marked **Deferred**.

No production database was touched to produce or verify this audit: verification ran against the real migrations replayed on an in-process Postgres (PGlite, via `npm test`) and against a locally-run demo-mode dev server (no Supabase credentials). See "Not verified" at the end for what that leaves out.

## P0 detail

### P0-1 — owner could self-approve a pending submission
`protect_app()`'s non-admin `UPDATE` branch checked `old.status = 'suspended' OR new.status NOT IN ('published','hidden')` and reverted the status otherwise — which does **not** cover `old.status IN ('pending','rejected') AND new.status = 'published'`, since `new.status` (`'published'`) *is* in the allowed set. An app owner could `UPDATE apps SET status = 'published' WHERE id = mine` and it would go straight through, regardless of `SUBMIT_REQUIRES_APPROVAL`. Fixed in `supabase/migrations/20260201000000_beta_hardening.sql`: non-admins may now only toggle between `published` and `hidden`, and only when the row is already in one of those two states.

### P0-2 — ownership assignment wasn't atomic, and could replace an existing verified owner
`verifyClaim` fetched the app, ran the domain check, then unconditionally wrote `developer_id`/`ownership_status` — with no check that `ownership_status` wasn't already `verified_owner`, and no locking between the check and the write. Fixed by `public.claim_app_ownership(app_id, user_id, claim_id)`: a single `UPDATE ... WHERE ownership_status <> 'verified_owner'`, which Postgres locks at the row level for its duration, so a second concurrent (or merely later) caller's `WHERE` clause simply no longer matches and the function returns `false`. `verifyClaim` now also fails fast, before even fetching the live page, if the app already has a verified owner.

### P0-3 — the third-party install dialog could install PWANova instead of the listed app
`InstallDialog` (used from every app page) called `window.addEventListener("beforeinstallprompt", …)` and, on Android, rendered a native "Install {App}" button wired to that event's `.prompt()`. The `beforeinstallprompt` event is scoped to the page that's currently loaded — i.e. PWANova's own origin — and cannot fire for a different origin PWANova merely links to. So on a browser where PWANova itself happened to be installable, clicking "Install Metro Fit" would silently trigger *PWANova's own* install prompt. Fixed by removing all `beforeinstallprompt` handling from that component; the only correct flow the platform allows — explain, then send the visitor to the app's own domain to install itself — is what it does now, with copy that says so explicitly ("You'll install it from **{domain}** — the steps happen on {App}'s own site, not on PWANova"). Guarded by `tests/install-dialog.test.ts`, a source-level regression check (there is no headless browser/DOM test harness in this project — see `docs/beta-pilot.md` for the real-device manual check this still needs).

## Ratings/reviews model (as implemented, not changed — documented here because the brief asked to verify it explicitly)

- One `ratings` row per `(app_id, user_id)` — enforced by a unique constraint. Changing your rating is an `UPSERT`, never a new row.
- At most one `reviews` row per `(app_id, user_id)` — same mechanism.
- A review's `rating` is copied into `ratings` by an `AFTER INSERT OR UPDATE OF rating` trigger (`sync_review_rating`), so a review always reflects a real, current rating and the two tables can't drift apart.
- Deleting a review does **not** delete the rating (they're different actions, and the UI doesn't offer a single button that claims to do both) — you can still see and change your star rating after removing your written review.
- `average`, `count` and the 5→1 breakdown (`rating_breakdown()`) are all computed from the same `ratings` table — never a mix of `reviews`-derived and `ratings`-derived numbers.
- The developer of an app can neither rate nor review it (now enforced in the database, not just the server action — see the audit table).

## Not verified (and why)

- **Live Supabase project.** `scripts/verify-supabase.ts` (34 checks against a real project — Auth, RLS, Storage, the atomic claim function, etc.) exists and is unchanged in capability, but per this stage's instructions ("without separate permission: don't touch the production database, don't run production migrations") it was **not run this session**. Everything above was instead verified against the real migration files replayed on a disposable in-process Postgres (`npm test`, PGlite) and a locally-run demo-mode dev server. Run `npm run verify:supabase` against a **non-production** Supabase project (or the existing one, with explicit go-ahead) before the pilot.
- **Google/GitHub OAuth sign-in**, magic-link email delivery, and Storage uploads need a real Supabase project with providers configured; not exercised this session for the same reason.
- **Real iOS/Android devices.** The install-dialog fix and mobile layout were checked with the emulated mobile viewport in this session's browser tool, not a physical phone. See `docs/beta-pilot.md`'s manual checklist.
- **`beforeinstallprompt` on a real Chrome/Android device** specifically — the regression test is a source-level guard (no such event exists in this project's test environment to fire); the fix is a straightforward removal of the handler, but a real-device click-through is still worth doing once.
- Ten real developer submissions and two real partner integrations (`docs/beta-pilot.md`) are the *goal* of the next stage, not something this session could produce.
